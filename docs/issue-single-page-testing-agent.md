# 单页测试代理：规划—执行功能需求

> 历史设计文档。当前实现见 `src/agents/single_page.py`。以下任务和验收条件描述初始提案，不能据此推断当前代码已全部实现。

## 概要与动机

探索代理适合快速发现多个页面，但可能在单个页面上停留不足，遗漏多步骤表单、条件显示组件和边界情况。单页测试代理应针对指定 URL 系统地覆盖表单字段、按钮、链接、弹窗、下拉菜单及页面内流程。

## 方案

代理分为两个阶段：

1. **规划**：分析页面结构和可交互元素，利用模型生成测试用例，按风险排序并估计覆盖范围和耗时。
2. **执行**：逐项准备状态、执行步骤、比较预期与实际结果、记录发现与截图；发现新状态时可补充计划。

~~~mermaid
graph LR
    A[打开目标页面] --> B[分析页面结构]
    B --> C[生成并排序测试计划]
    C --> D[执行用例]
    D --> E[验证结果]
    E --> F[记录发现]
    F --> G{还有用例吗}
    G -- 是 --> D
    G -- 否 --> H[汇总结果]
~~~

## 原提案的实施任务

### 阶段一：基础结构

- 建立 `SinglePageTestingAgent` 与规划—执行循环。
- 定义 `SinglePageTestConfig`、`TestCase`、`TestPlan`、`TestResult`、`SinglePageTestState` 和 `PageSnapshot`。
- 保存测试计划和会话状态。

### 阶段二：测试规划

- 提取表单、输入框、按钮和链接，识别元素关系及动态组件。
- 生成有效、无效和边界输入用例，以及按钮、导航与多步骤流程用例。
- 识别登录、结账和数据提交等关键路径，按风险安排执行顺序。

### 阶段三：测试执行

- 按顺序执行步骤，准备和清理页面状态。
- 比较预期结果与实际结果；捕获控制台、网络、校验及视觉问题。
- 处理执行错误，并在用例之间重置页面状态。

### 阶段四：报告与接入

- 汇总通过与失败的测试、覆盖指标和截图，并支持计划导出。
- 在命令行中提供单页模式、策略选择及会话管理。
- 编写使用说明和接口文档。

## 核心数据

`TestCase` 包含 `id`、`name`、`description`、`priority`、`category`、`steps`、`expectedOutcome` 及可选的 `preconditions`。优先级使用 `critical|high|medium|low`，类别使用 `form|navigation|interaction|validation|visual`。`TestPlan` 记录 `pageUrl`、`pageTitle`、`totalTests`、`testCases`、覆盖统计和预计耗时。字段名作为程序接口保留英文；展示名称和描述使用中文。

## 原提案的验收目标

- 可以分析任意目标页面并生成结构化测试计划。
- 计划覆盖可交互元素，执行结果可保存、复查和重跑。
- 自动识别常见问题，并在命令行中展示结果。
- 统计交互元素覆盖率、单页独立问题数、耗时、重跑能力及新发现元素的覆盖率。

这些是原需求目标，当前实现是否达到应以代码和测试结果为准。

## 待决事项

- 复杂状态如何设置前提条件，例如登录前后、空购物车与非空购物车？
- 测试数据由模型生成还是由用户提供？
- 哪些用例可以安全并行执行？原提案建议先顺序执行。
- 如何与多页面探索代理协作？原提案建议先保留独立模式，之后考虑混合模式。
