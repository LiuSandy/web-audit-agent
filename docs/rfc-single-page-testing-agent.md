# RFC：采用规划—执行架构的单页测试代理

> 历史设计文档。当前实现见 `src/agents/single-page.py`；本文是设计背景，具体行为以代码为准。

**状态：**草案  
**作者：**Crisler Wintler  
**创建与更新：**2026-01-08

## 摘要

单页测试代理针对一个指定页面进行深入测试。它先分析页面并生成计划，再逐项执行、验证和记录结果。多页面探索代理侧重发现站点范围内的页面；该提案希望补足单页内的复杂交互、条件状态和边界输入覆盖。

## 动机

原探索流程可能快速离开当前页面，无法完整覆盖多步骤表单、弹窗、下拉菜单、按钮结果和不同登录状态。系统化的单页计划需要：

- 枚举表单字段、按钮、链接及可见的动态元素。
- 为有效、无效和边界输入生成测试。
- 验证导航、可见反馈和页面状态变化。
- 覆盖同一页面内的多步骤流程。

## 设计流程

~~~mermaid
graph TD
    A[打开目标页面] --> B[分析可交互元素]
    B --> C[生成测试计划]
    C --> D[按风险排序]
    D --> E[准备用例状态]
    E --> F[执行步骤]
    F --> G[验证预期结果]
    G --> H[记录结果与发现]
    H --> I{还有用例吗}
    I -- 是 --> E
    I -- 否 --> J[汇总测试结果]
~~~

### 规划阶段

1. **页面分析**：提取表单、输入框、按钮、链接及其关系；识别弹窗、下拉菜单和条件显示状态。
2. **用例生成**：覆盖表单校验、按钮点击、导航目标、可见错误、特殊字符、空值与最大长度，以及多步骤交互。
3. **优先级排序**：登录、结账和提交数据为关键路径；主要用户流程为高优先级；次要功能和外观问题随后执行。

### 执行阶段

每个用例依次准备前提条件、执行步骤、比较预期与实际、保存结果，并在必要时重置页面。验证内容包括控制台错误、网络失败、表单校验提示、破损图片、布局问题和意外导航。若执行时出现新的元素或页面状态，原提案建议将相应测试加入计划。

## 核心组件与数据

`SinglePageTestingAgent` 管理浏览器、页面、模型、计划和结果。原提案将页面分析、测试规划、执行与验证拆成独立工具；当前 Python 版本主要集中在 `src/agents/single-page.py`。

| 数据结构 | 主要字段 |
|---|---|
| `SinglePageTestConfig` | 目标 URL、策略、最大用例数、认证与可选视觉检查配置 |
| `PageSnapshot` | 页面标题、URL、交互元素及可见性 |
| `TestCase` | `id`、中文 `name` 与 `description`、`priority`、`category`、`steps`、`expectedOutcome` |
| `TestPlan` | 页面信息、用例列表、覆盖统计与预计耗时 |
| `TestResult` | 状态、耗时、执行步数、错误和发现 |
| `SinglePageTestState` | 当前阶段、用例索引、计划、结果与会话信息 |

内部状态与枚举（如 `passed`、`failed`、`high`）是稳定接口；面向用户的文字使用中文。

## 原提案的实施阶段

1. 建立代理类、数据类型和基本规划—执行循环。
2. 开发页面分析、模型规划、优先级排序和计划保存。
3. 开发执行、自动验证、状态重置与截图。
4. 汇总报告，接入命令行，并考虑计划导入和导出。

## 权衡

**优点：**单页覆盖更系统，可发现复杂交互问题；计划可保存和重跑，并可根据发现调整。  
**成本：**执行时间与模型调用增加，状态管理更复杂；单页模式无法独自验证跨页流程。

原提案建议提供可配置深度、缓存页面分析，并在未来与探索模式组合。独立用例是否可以并行执行，需要根据页面状态隔离能力判断。

## 成功指标与待决事项

关注交互元素覆盖率、每页独立问题数、完成耗时、计划重跑能力和动态元素覆盖率。仍需确定登录态等复杂前提条件、测试数据来源、并行安全性、与探索代理的协作方式，以及报告的详细程度。

## 方案选择

原提案比较了扩展探索代理、固定脚本和混合模式。独立单页代理更便于维持“广度探索”与“深度测试”的不同目标；后续可考虑混合模式。
